# Splitty Multiplexer Architecture

## Overview

Splitty is a terminal multiplexer with a web-based frontend (Svelte 5 + dockview) and a Rust backend (Tokio + Axum). The backend owns layout and session state. The frontend renders it and sends layout changes as fire-and-forget operations.

## Ops Model

Layout changes are expressed as **Operations** — typed structs that describe a mutation (`split_pane`, `close_pane`, `move_pane`, etc.). There is no CQRS-style separation between Commands and Events.

The flow is Redux-like:

```
Op → Validate → Reduce (pure) → new State + Effects
```

The Reducer is a pure function: `(ScreenState, Op) → (ScreenState, []Effect)`. Effects (`SpawnSession`, `KillSession`) are executed separately by the EffectRunner (`mux::effect_runner`) — no I/O inside the Reducer.

An op is always "I want this to happen." Whether the client applies it optimistically or the server applies it authoritatively doesn't change the wire format. This makes the protocol multiplayer-ready without structural changes — only the delivery semantics change (fire-and-forget → ACK/REJECT).

## Client Autonomy (Shadow Mode)

The client is autonomous for interactive layout decisions. Dockview handles splits, resizes, and tab moves locally. After each interaction, the client sends a `mux.op` fire-and-forget. The server updates its model and sends no acknowledgement; it answers only with the `mux.pane_spawned` events the op causes, or with `mux.op_failed` when it rejects an op that would create a pane or an `arrange_panes`.

Splits, new tabs and closes have ops of their own. Drags and divider moves do not map onto `move_pane` and `resize_split`. Drags are a tab or a group into another group, or to a group's or the screen's edge. Dockview's grid and the server's tree can show the same picture with different trees: dockview keeps one row where the server nests splits of the same axis. The window also does not learn the node IDs the server creates. So after such a gesture the bridge (`bridgeDockviewToMux` in `lib/connection/screen_binding.ts`) waits 100 ms. It then reads the grid from dockview's `toJSON()` (`layout/arrangement.ts`) and sends it as `arrange_panes` when it differs from the arrangement the screen's binding last saw in a snapshot or sent. It sends nothing to a server without `layout-arrange-v1`, while the screen has a maximized or popout group, or for a move made by a snapshot rebuild.

A tab click moves nothing, so it sends no arrangement. In the same 100 ms step the bridge goes through the screen's groups with two or more tabs, in the grid or floating. It sends `select_tab` for each one whose shown tab is not among the active tabs the binding knows the server has: those of the last snapshot, of every arrangement and `select_tab` sent since, and the new pane of every `new_tab`. A removed panel triggers the same step, because dockview shows a neighbour of the closed tab and the server the first remaining one. The server sends no nudge for `select_tab`: other windows keep their own tabs through a snapshot anyway, and they see the choice when they build the screen anew. A fresh build shows each slot's active pane, or its first one when the slot names none. Servers without `tab-select-v1` get nothing.

The reducer replaces the root layout only when the tree holds exactly the root layout's panes. Pane IDs the screen does not hold are left out first, such as a pane that spawned its own session after a rejected op. A rejection comes back as `mux.op_failed`, and the mux client resyncs the screen, so the window shows the server's layout again at once. Floating groups are not part of the arrangement; their buttons keep `float_pane` and `dock_pane`.

This works because:
- **No screen ownership** — every connected client may change every screen; the server applies ops in arrival order and rejects invalid ones atomically (for example `create_screen` over a screen that still has panes)
- **Client-set IDs** — the client generates pane/screen IDs, no round-trip needed
- **Server-owned sessions** — the server spawns and kills the sessions of mux panes, so a client never has to create one before its pane exists on the server

`move_pane_to_screen` is a workspace op without effects: the reducer takes the pane and its session record out of the source like `close_pane` would, without `KillSession`, puts it into the target's first slot or a new screen, and removes a source left empty. The client that moves a pane hands it over instead of closing it: `ScreenBinding.handOver` makes the bridge skip the panel's `close_pane` and `release` detach its session rather than close it, `ScreenViews.reveal` shows the pane in front once the target's snapshot holds it, and `ScreenStartup.expect` / `RemoteScreenSync.adopt` keep a target the op creates from getting a `create_screen` of its own or being flagged missing. Other clients get `mux.nudge` for both screens and rebuild them from their snapshots. A pane's shell keeps the `SPLITTY_SCREEN_ID` it started with, so a screen op from the CLI that names a screen no longer holding its pane is applied to the screen that does; an owner's job placement follows the pane the same way, an agent's grant anchor does not.

Every op runs its effects, whether it arrives over the WebSocket, from the CLI (`POST /api/mux/op`) or through the control socket. For a pane it created, the client waits for `mux.pane_spawned` and attaches to that session through the session protocol. Only when the op is rejected or no `mux.pane_spawned` arrives in time does the client send `create` itself; the server resolves a pane it knows to that pane's session, so the fallback does not start a second shell.

### Start-up and reload

The screens store starts with a placeholder screen, and `lib/mux/screen_startup.ts` decides how each local screen gets its content. Before the first `mux.welcome` nothing is created. Screens the welcome lists, or a snapshot names, are built from their `mux.screen_snapshot` only, also when their view is ready first; a placeholder the welcome does not list is dropped. Only when the welcome lists no screens, and for screens the user creates later, does the client add a first pane and send `create_screen`. The connection's mux client (`lib/mux/mux_client.ts`) additionally holds back every `create_screen` until that connection's current welcome. The server rejects `create_screen` for a screen that still has panes and re-creates a screen that ran empty in place.

### Attaching to sessions

`lib/terminal/attach_registry.ts` routes every binary frame. Before rendering historical frames (those received before `attached`), `replay_output.ts` removes clipboard operations and terminal report requests such as OSC color queries so restoring a view cannot type their replies into the current shell. Live frames remain unchanged, even when buffered until the view is wired. A connection keeps at most one `attach` per session in flight; frames for that session are buffered from the `attach` until its view is wired, because the replay arrives before `attached`. A newer view of the same session (a snapshot rebuild of a pane whose attach is still in flight) takes the attach over, and the older one gets `AttachTransferredError`. `detach` goes out only when no view holds or waits for the session, since the server streams a session at most once per connection.

Once an attached view is wired, it measures its pane again and reports that size with `resize`, which accounts for layout changes during the attach. A server announcing `pty-size-v1` sends the session's `size` before the replay, so the emulator has the PTY's size before the buffered output is written, and the first report carries `redraw`: when the PTY size does not change, the server resizes the PTY by one row and back itself, so TUIs redraw after the replay. With an older server the view resizes the backend PTY by one row and back to its grid size, keeping the emulator's dimensions; using `resize` also works with servers that ignore dimensions on `attach`.

## PTY Size

Several connections may show one session, and the PTY has one size. With `pty-size-v1`, `resize` is a report: the size at which the connection shows the session. `protocol::sizing::SizeArbiter`, owned by the dispatcher, keeps per session each connection's report and per connection its activity, and derives the PTY size with the server's `terminal.size_policy`: the smallest columns and rows of the active connections (`active`, the default; a connection is active within `terminal.size_idle_seconds` of its last `activity`, unless it sent `idle` since or another one took over), of the most recently active one (`latest`), or of all (`smallest`); with no active connection, the most recently active one decides. Computing the size, resizing the PTY and publishing the new size on the session's watch channel happen under one lock; every stream of the session forwards a published size as a `size` event, and a one-second tick (spawned with the first connection, holding the dispatcher weakly) settles connections that became idle. Settings updates reconfigure the arbiter. A connection that never sent `activity` or `idle` is an older client: each of its reports counts as an activity.

The client decides what counts as activity, because the server cannot: an emulator answers terminal queries through `input` on its own. `lib/terminal/presence.ts` sends `activity` for a key, a pointer button, the window gaining focus or being resized (not for scrolling), only to the active screen's connection and at most every 5 seconds, `idle` to every connection when the window is hidden, and greets each welcome with `activity` or `idle` before anything is attached. A pane is shown while its panel is visible on the active screen; a terminal session reports its pane's size only while shown, sends `hide` when it stops being shown (screens in the background stay laid out behind the active one and would otherwise keep counting), and keeps two sizes apart: the pane's, measured with `measure()` and reported, and the PTY's, from `size`, which its emulator always has. Emulator resizes are not reported, or pinning the emulator would report the PTY's size as the pane's. While the pane's own report decides, a new pane size is applied at once and corrected by the server's answer. `panes/pty_size_marker.ts` hatches the area outside a smaller terminal, moves a taller one up as far as its cursor's row needs (as tmux does) and shows the size in a badge that takes the size over (`activity` with `takeover`).

## Two Protocol Paths

Splitty has two coexisting protocol layers on the same WebSocket:

| Layer | Messages | Purpose |
|-------|----------|---------|
| **Session protocol** | `create`, `attach`, `input`, `output`, `resize`, `close`, `save_image`, `upload`, `file.*`, `activity`, `idle`, `hide`, `size` | PTY I/O — `output` uses binary WS frames; rest is JSON |
| **Mux protocol** | `mux.op`, `mux.resync`, `mux.welcome`, `mux.screen_snapshot`, `mux.nudge` | Layout state — screen/pane management |

The mux handler intercepts `mux.*` messages; everything else falls through to the session protocol handler. Both share one WebSocket connection.

The web frontend is not the only client of the session protocol. `splitty attach` (`cli::attach`) shows one session in the terminal it runs in, next to the windows that show it: on `mux.welcome` it sends `activity` with `takeover` and `attach`, runs the replay through the same filter the web client applies (`pty::replay`: no report requests, no clipboard writes), then reports its terminal's size with `resize` and the user's typing with `activity`, and detaches with `detach`. It ignores the mux messages. Like `remote-bridge`, it opens the daemon's WebSocket on this machine with the token file, a single-use ticket and the daemon's own origin (`cli::socket`), so no new route or credential path exists for it; the server keeps owning the session.

### Connection Lifecycle

1. Client opens WebSocket
2. Server sends `mux.welcome` with `clientId`, `screens[]`, and `serverMode` ("embedded" or "daemon")
3. Client creates local screens for any server-known screens, requests state via `mux.resync`; until this welcome it sends no `create_screen` (see Start-up and reload)
4. Server responds with `mux.screen_snapshot` containing full layout tree
5. Normal operation: client sends `mux.op` fire-and-forget, server mirrors state

No mux-level attach/detach — the client gets screen state via `mux.resync` on demand.

### Client connections

The client holds one `ServerConnection` (`lib/connection/`) per server it shows screens of: the local server, the connection `local`, and one `host:<target>` per host with screens in the window, once one of them was shown (see Remote Screens). A connection owns everything that speaks to its server: the socket, the mux client, the attach registry, the session client (`create` queue, sessions, which pane shows which session, the server's home directory) and the handlers of its server commands. The local socket alone treats a failed open as an expired login and queues messages while it is down; a host's socket has rules of its own. A lost connection fails the attaches in flight on it, so the views rebuilt after the reconnect send their own.

Every screen of the window is bound to its connection by a `ScreenBinding`. A local screen's key is its id on the local server; a screen of another connection gets a random key of its own and keeps its id on that server (its wire id) apart, so nothing a server sends becomes a local identifier. Panes, tabs, context menus, the close guard and the templates find their binding from dockview's layout API (by the layout's id, since dockview hands group headers and the watermark API wrappers of their own) and reach sessions and ops only through it; a pane whose layout has no binding is not mounted. The binding also holds what is per screen: the flag that holds back layout ops during a snapshot rebuild, the floating-entry ids, and the teardown, which says whether removing the screen's layout closes its sessions (local screens) or only detaches them.

The routing rule: a message is resolved only against the objects of the connection it arrived on. Output, `attached`, `closed`, `title`, `mux.pane_spawned` and `mux.op_failed` reach only that connection's views, sessions and spawn waiters. A welcome, snapshot or nudge reaches the connection's screen sync: the local server's goes through `ScreenStartup`, any other's only touches screens already bound to it (`lib/connection/screen_sync.ts`). Notifications carry their connection, and another server's are titled with its name. Server commands go through one resolver (`lib/connection/routing.ts`): they act only on panes of the sender's screens, without a pane id only when the active screen is the sender's, and never switch screens; `pane.paste` from a server other than the local one is refused, and its `pane.copy` follows `terminal.allowOsc52Write`. Names, titles and notifications from any server are plain text with length caps (`lib/protocol/untrusted.ts`), and a malformed message or a failing handler never stops the socket's other handlers.

Inactive screens are `inert`. A terminal takes the keyboard only while its screen is the active one, so a snapshot rebuild of a hidden screen cannot pull typing there; when a screen becomes active, its active pane takes the keyboard.

## ID Ownership

Pane and screen IDs are **client-generated** and random (`terminal-<16 hex>`, `screen-<16 hex>`, `lib/ids.ts`); only the "Screen N" names are numbered: the lowest number from 2 that no screen of the window uses, nor, for a new screen on a host, one of that host's screens (`stores/screens.svelte.ts`, `nextScreenName`). The client includes them in ops via `newPaneId` and `screenId`. The server uses them as-is, but rejects a `newPaneId` that already names a pane anywhere in the workspace (`mux.op_failed`). If omitted (CLI-initiated ops), the server generates IDs.

This eliminates round-trip latency: the client creates a dockview panel and assigns its ID before the server even processes the op.

## CLI Flow

`splitty agent guide` is an offline CLI operation, handled before server discovery
and allowed as local information under scoped invocation. Its versioned Markdown
is embedded in the CLI; `--json` wraps that same text as `{version, guide}`. It does
not read server configuration, connect to an owner socket, or inject an agent prompt.

New PTYs discover an executable `splitty` in the host executable's installation
directory (the server itself, or a sibling of the native GUI). They prepend that
directory to their child PATH once and supply the non-secret `SPLITTY_CLI_DIR`
hint. A starting daemon first points `bin/splitty` of its run directory at its own
CLI (`cli_path::publish_stable_cli`, a link renamed into place); a spawner hands out
that `bin/` directory instead of its own while the link resolves to the same file as
its CLI, so a kept shell, or an agent started in one, reaches the next daemon's CLI
after an update. Bash restores it after its existing startup replay, and Zsh at its prompt
hook after user startup. The common PTY spawn path removes stale inherited hints;
no shell configuration or server-global environment is changed. `agent exec` uses
the same directory/PATH helpers for its child while retaining its grant-only socket.
GUI-only packages without an installed/bundled CLI keep their existing PATH; no
fake GUI alias or runtime CLI installation is created.

CLI commands use the shared HTTP API over an owner/scoped Unix socket, or an explicitly
authenticated TCP connection. Layout commands post `/api/mux/op`; the reducer applies the
intent, the effect runner returns actual outcomes, and clients receive successful spawn
mappings followed by a nudge naming the actual screen. No UI is needed to start a process.
Queries read the authoritative screen/workspace state. `reqwest` handles framing on both
transports, with bounded responses, a deadline, no redirects and no environment proxy.

### Managed jobs and local agent grants

`splitty_server::jobs::Jobs` owns accepted start tasks, idempotency, live handles and
authorization. Every `WsState::new` wires the same coordinator, including Tauri embedded
servers. Metadata remains in the pure mux store; clocks, PTYs, socket lifetimes and waiters
remain outside it. Typed effect outcomes prevent false successful-spawn events. A bounded
injected notification channel delivers job changes without a dependency back into `ws`.

The owner socket alone provisions/revokes grants and transfers jobs. A grant has its own
private listener and fixed job-only router. Listener identity supplies the principal;
JSON never does. Grant read/write gates and per-job lanes order input, transfer and revoke;
pending input also checks its authorization epoch. Log waits release action gates, hold
bounded semaphore permits, and reauthorize when they return. Weak coordinator references
in grant routers avoid listener/service reference cycles. Accepted spawn work survives a
request disappearing, while server shutdown closes admission and stops managed processes.

Directory validation runs outside admission/authorization locks, in a bounded blocking
pool with a three-second request deadline, followed by reauthorization. Managed PTY
masters use nonblocking writes so a program that never reads stdin cannot pin a grant's
action gate indefinitely. Their single reader waits with `poll` on an owned descriptor;
ordinary shell PTYs retain their existing blocking reader. A full input buffer reports
an I/O error synchronously rather than leaving an input task that could write after revoke.

Job snapshots project only bounded lifecycle metadata alongside pane job IDs, not every
stored launch argument. The incoming-message validator preserves these fields and fails
closed on unknown states. Background job additions/metadata updates preserve existing
terminal renderers, tabs and keyboard focus; failed/interrupted job views never create a
shell. New remote screens retain explicit host-directory/reopen semantics.

## 2D Grid Projection

`crates/splitty-core/src/mux/grid.rs` projects the layout tree into a flat list of `PaneRect` structs with relative coordinates (0–1). Each rect has `{pane_id, slot_id, x, y, w, h}`. Stacked panes in the same slot share identical rects.

`find_neighbor(root, pane_id, direction)` uses the grid with a 90° cone filter — identical logic to the frontend's `findNeighborGroup()`.

## MuxManaged Flag

When mux is active, `Connection.mux_managed = true`. This tells the session protocol's `Connection::close()` to NOT kill PTY sessions on disconnect — only output streams are canceled. PTY sessions continue running independently.

## Session Output

A `Session` (`pty/session.rs`) is the session layer over a terminal (`pty/terminal.rs`): the session builds the spec (program, the full environment, directory, size, managed or not), and a terminal factory starts the program on a PTY, in this process (`LocalTerminal`, embedded servers) or in a session keeper (`keeper::client::KeptTerminal`, daemons; see Session Keepers). Either feeds the session every chunk of output from the first on (`Feed`): it goes into the scrollback ring buffer, through the OSC scanner (title, OSC 133, bell watch channels) and to each subscriber, all under one output lock. The local terminal reads the PTY on its own reader thread, `pty-reader-<id>`, until EOF whether or not any client is connected. So output is captured, prompts are tracked and a busy process never blocks on a full PTY buffer while nobody watches.

Connections never read the PTY. `SessionHandle::subscribe()` returns the scrollback snapshot and an unbounded receiver for later chunks, taken under that same lock, so replay plus live stream contain each byte exactly once. `handle_create` and `handle_attach` send the snapshot in 32 KiB frames (attach: before `attached`), then `stream_output` forwards the receiver. Detaching, disconnecting or replacing a stream only drops that subscription; the reader is untouched, and any number of connections can stream one session. Stopping a connection's stream (detach, a replacing attach, close) waits until its task has ended, so nothing it was forwarding arrives after the next response. Once the output has ended or the process has exited, `stream_output` waits up to 2 s for the other before sending `closed`, so the exit code is known; the notification engine hears of the exit once per session (`claim_exit_report`).

The reader thread holds its own descriptor of the PTY master, so `close` hangs up the terminal explicitly (SIGHUP to the shell and the foreground process group) and the thread ends at the EOF that follows. A stopping embedded server closes all sessions this way after its server has stopped; otherwise a session still held by a client connection would keep its shell, and with it the process, alive. A stopping daemon releases its sessions instead (`Backend::release_all`): the keepers keep the programs running for the next daemon.

## Session Keepers

In daemon mode every session's PTY and program belong to a keeper process of their own (`splitty_core::keeper`), so a daemon restart, an update or a daemon crash ends no session. The keeper owns the process and its terminal; the daemon is its controller; clients connect to the daemon as before, which keeps the dispatcher, the effect runner and the jobs coordinator unaware of keepers (they see `SessionHandle`s).

- **Start.** The daemon's terminal factory (`keeper::client::Keepers`) runs its own executable as `splitty session-keeper` with `setsid`, a socket pair on standard input and standard error shared with `daemon.log` (`ProcessLauncher`, which also reaps the keepers it started while it runs; after the daemon exits, init takes them). `main` dispatches the subcommand before it builds the Tokio runtime: a keeper is a few blocking threads. The daemon sends the spawn spec over the socket pair, never on the command line; the keeper binds its socket, starts the program with exactly the spec's environment and answers `hello` with the PID, or `spawn_failed`, which tells a program that could not start (the session's error) from a keeper that could not set itself up (the session then runs in the daemon, with a warning in the log). The socket pair stays the daemon's controller connection.
- **Where.** `config::run_dir()` is `$SPLITTY_CONFIG_DIR/run` or `<user data dir>/splitty/run`, not `$XDG_RUNTIME_DIR`, which systemd-logind removes at the last logout while a remote host's daemon keeps running. Keepers sit in its `keepers/` (0700, sockets 0600), named after the first 16 letters and digits of the session id (a socket path is limited to 103 bytes on macOS); both sides check the peer's user id (`keeper::dir`).
- **Protocol** (`keeper::wire`). Frames of a 4-byte big-endian length, a kind byte and a payload, at most 1 MiB: JSON for control frames, raw bytes behind a sequence number (`input`) or an absolute offset (`output`). On every connection the keeper speaks first with `hello`. A controller claims (`claim`, optionally with `takeover` and the offset to resume from) and the keeper answers `claimed` or `busy`; a takeover tells the previous controller `taken_over`. The keeper reports `input_result` per write (blocking for ordinary sessions, failing at once on a full PTY for managed ones), `foreground` when the terminal's foreground process group changes (it checks twice a second; the session layer used `tcgetpgrp` on its own master), `exited` when the program has ended and `output_ended` when the terminal closed: two events, as the session layer has them. Version 1 is meant to last; changes stay additive.
- **The keeper** (`keeper::process`). It reads the PTY into an offset ring of the session's buffer size and queues frames per controller on a writer thread of their own; a controller more than 8 MiB behind is disconnected and resumes at its last offset (`KeptTerminal` reconnects with `takeover` from the offset it has, so its session sees no byte twice). `pty::lifecycle` runs in the keeper unchanged, which is the program's parent and so has the real exit status. Once the program has ended and its terminal closed, the keeper waits for `exit_ack` from a controller that recorded both (or `close`, or seven days without one), then removes its socket and exits.
- **Adoption.** A starting daemon reads the keepers directory (`keeper::client::find`), leaves keepers of another protocol version running, takes the others over before it loads the workspace (`Found::take_over`), applies `daemon::restore_jobs` with the adopted session ids (their jobs keep running), builds its state, registers a session on every adopted keeper (`Manager::adopt`, fed from the keeper's oldest buffered byte, so scrollback and OSC state come back; a keeper the workspace does not know becomes a session without a pane), lets the jobs coordinator watch the adopted jobs again (`Jobs::resume_adopted`), and only then respawns, through `restore_effects`, the sessions the backend does not hold.
- **Stop.** `daemon stop` and SIGTERM release the keepers; job grants are revoked (`Jobs::release`), job processes run on. `daemon stop --end-sessions` then takes every keeper over and sends `close`, also without a daemon; `daemon restart` stops and starts the invoking binary on the old port. The daemon's control socket is `daemon.sock` in the run directory (`control::daemon_socket_path`), so an adopted shell's `SPLITTY_SOCK` reaches the next daemon; `daemon.json` says `keepsSessions: true`.
- **Attach without a daemon.** `splitty attach` lists the keepers by their `hello`s (the working directory looked up by PID) and claims one without `takeover`. When a starting daemon takes the keeper over, the command waits for the daemon and continues through its session stream, dropping that stream's replay.

Managed jobs use a direct argv launch in that same PTY layer, bypassing shell profiles, login arguments
and delayed command injection. The process environment/PATH is the server's; an explicit shell in argv
is the only source of shell interpretation. A single lifecycle worker owns process signalling and
reaping. On Unix it observes structured exit/signal status with `waitid(WNOWAIT)` before `waitpid`, so
a managed stop can retain the unreaped launch leader's identity through TERM, the three-second grace
period and KILL escalation of its launch process group. No saved foreground PID is used for managed
stop. Processes that escape that group are not a containment guarantee. Stopped job output remains
available; process completion and output EOF are separate facts. Ordinary close still resolves its
foreground group from an owned terminal descriptor for SIGHUP. Exit events carry the actual code or
signal rather than turning every failure into -1.

Managed output has two bounded rings: raw PTY bytes and incremental sanitized UTF-8 log text, each
using the configured scrollback capacity. The `vte` parser has its `std` feature disabled and an OSC
buffer of zero bytes; sequence payloads never accumulate. C1 controls are normalized without treating
Unicode continuation bytes as controls. Text retains printable Unicode, tabs and normalized newlines
(CRLF becomes one newline), not cursor placement or a reconstructed TUI screen. A cursor includes its
job, fresh output generation, representation and absolute byte position. Reads cap returned bytes,
report overwritten positions and keep UTF-8 boundaries. A long poll watches a bounded change signal
before reading, rather than adding an unbounded output subscription. EOF and the ring snapshot are
read under the capture lock together so a reader cannot miss final bytes by observing a newer EOF.

## Session Scratchpads

Every terminal session carries one plain-text scratchpad (`session-scratchpad`) in its record of the mux model, `SessionEntry::scratchpad`, so it lives exactly as long as the session: it survives the process exiting, moves with its pane to another screen, is persisted with `state.json` and comes back with a kept or respawned session, and ends with `close_pane`. A window replaces it whole with the screen op `set_scratchpad` (at most 64 KiB of UTF-8); the WebSocket handler nudges the screen's other clients, which find the text in their next snapshot, and `mux.welcome` announces `scratchpad-v1`. The window is the only channel: `POST /api/mux/op` refuses the op, and `GET /api/mux/state` and `/api/mux/screen/{id}` leave the text out (`http::routes::without_scratchpads`), so an agent that reads the workspace through the control socket never sees text the user wrote for later.

In the window, each `ServerConnection` holds a `Scratchpads` store (`lib/scratchpad.ts`) fed by that server's snapshots: an edit shows at once and is saved half a second after typing pauses, a newer text from the server replaces the shown one only while no edit of this window waits, and for a moment after a save a snapshot the server made before it cannot take the text back. `TerminalPaneRenderer` puts the area (`panes/scratchpad_area.ts`) below the terminal box, which holds the terminal and its overlays; whether it is open and how tall it is belong to the window, per session. The shortcut, the pane group's header button, the pane menu and the palette reach it through a registry by pane id, the tab shows a marker while text is held, and the close guard and the quit confirmation count scratchpads with text.

## Pasted Images

A program in a pane often takes an image as a path: Claude Code turns a bracketed paste of an absolute `.png`, `.jpg`, `.gif` or `.webp` path into an attachment. Its own Ctrl+V reads the clipboard of the machine it runs on, which on a host is empty. So the client puts a pasted or dropped image on the pane's own server and pastes the path (`lib/terminal/image_paste.ts`, wired per pane in `terminal_mount.ts`). The image comes from the browser's `paste` and `drop` events, the only way the page gets it, since its Permissions-Policy has `clipboard-read=()`. Ctrl+V (not on macOS) skips the terminal's own key handling when the focus is in an element the browser pastes into, so the browser's paste follows: with an image and no text it is uploaded, otherwise the client sends `^V` itself, also when no `paste` event arrives within 300 ms. The native paste shortcut and drops behave the same, without the `^V`.

`SessionClient.saveImage` sends `save_image` (base64, at most 10 MiB, which stays under the 16 MiB the hub and the bridge carry) on the pane's connection and waits 30 s for `image_saved` or `image_failed` with its request id; a server older than `save_image` answers "unknown message type", which a waiting `create` ignores and the client reports as needing an update. The answer's path must be absolute and plain text, since it comes from the host. Neither socket queues `save_image` while it cannot send. On the server the dispatcher hands the image to the protocol's paste store, which checks the leading bytes, stores it under a name of its own in `splitty/paste/` of the cache directory (0700, the file 0600, created new) and first removes pastes older than 24 hours and beyond the newest 100. The hub relays both messages like any other.

## File Transfers

Other files take the same way as pasted images, in chunks, and come back the other way on the user's Save.

**Into a pane.** A drop onto a pane or a scratchpad, or a paste of files without text, sends images with `save_image` and every other file with `upload`: `SessionClient.uploadFile` reads the file in slices of 1 MiB and sends each as base64 only after the server answered the last (`upload_progress`, then `upload_saved` with the path, or `upload_failed`), so one large file never holds up the pane's connection for more than a chunk, and every message stays far below the 16 MiB of the hub and the bridge. The dispatcher hands the chunks to the protocol's upload store (`protocol::upload`), which creates a new `upload-<time>-<hex>/` directory in the paste directory per upload, writes the file under a name it sanitizes itself (letters, digits, `.`, `-`, `_`), checks offsets and the size of 512 MiB, removes failed uploads and a closed connection's unfinished ones, and first removes `upload-` directories older than 24 hours and beyond the newest 100. Neither socket queues `upload`.

**Out of a pane.** `splitty download <file>` posts the session ID and the file's absolute path to `POST /api/file/offer` over the owner control socket (grant sockets do not route it). For a folder, `cli::download` first packs a zip into a new `download-*` directory of `<cache>/splitty/download/` and offers that; the directory goes when the command ends (on SIGINT, SIGHUP and SIGTERM as well), and one left by a killed command goes with the next folder download after 24 hours. The server and the window see only a file. `ws::files`, beside `ws::editor`, opens the file once, and sends `file.offer` to every connection that registered (`file-offer-v1`, `file.register`) and streams that session. The first `file.accept` takes the offer and the others get `file.closed`; the accepting connection reads it with `file.read` at the next offset, answered by `file.chunk` (1 MiB, base64, `eof` on the last), and the HTTP request answers `saved` after the last chunk. Offers expire after 60 s without an answer and 60 s without a read. In the window, `lib/file_offers.ts` treats offers as untrusted data, shows at most three with Save and Dismiss, and on Save reads the chunks, makes a `Blob` and saves it through a link with `download`. The Tauri shell allows downloads only of `blob:` URLs of its backend origin. Only the shell learns where a download went: Tauri's download hook and Electron's `will-download` remember the most recent 32 finished downloads of the main window by URL (`downloads` in both shells), and the "Saved" notice's Show in folder passes that `blob:` URL to `reveal_download` or `download:reveal`, which show the file in the file manager without telling the page its path.

## Server Modes

### Managed-job restore

The workspace's `jobs` map stores direct launch metadata and terminal outcomes, while job panes and
sessions carry a job ID and sessions explicitly use `restartPolicy: never`. Daemon restore marks
unfinished jobs `interrupted` unless the daemon adopted their keeper (then they keep running, under
trusted administration), keeps recorded terminal results, and never produces spawn effects for a job
(even if its stored session status is stale). Legacy states without jobs retain ordinary shell
restoration. Any surviving job reference or never-restart marker prevents a damaged record from
turning into an interactive shell. Client restarts are different: the running server keeps the job.
Output and live agent authority are not persisted. Before downgrading to a binary without job support,
stop managed processes and back up/reset the newer workspace; an older server cannot interpret these
panes safely.

Persistence is a server-mode property, not per-screen:

| Mode | `serverMode` | Behavior |
|------|-------------|----------|
| **Embedded** | `"embedded"` | Server dies with the window/process. Tauri embeds it on macOS/Linux; Windows launches it in the selected WSL 2 distribution and closes it through the desktop stdio bridge. |
| **Daemon** | `"daemon"` | Server runs as background process. State persisted to `state.json` after every dispatch. Sessions run in keepers, which outlive the daemon and which the next daemon adopts; only sessions whose keeper is gone are respawned |

The Tauri desktop app checks for a running daemon on startup. If found, it connects to the daemon instead of spawning an embedded server. When none runs but kept sessions of an earlier daemon wait (`keeper::client::find`), it starts a daemon first, with the executable a keeper names in its `hello` (the app bundle has no `splitty`), else `splitty` from its login `PATH`, so a crashed daemon's sessions come back with the app.

**Login shell `PATH`.** Started from the Dock, the Finder or a Linux desktop launcher, the Tauri app has the launcher's `PATH` (macOS: launchd's `/usr/bin:/bin:/usr/sbin:/sbin`), not the one the user's shell startup builds, and so has everything it starts without a shell: `ssh` and the `ProxyCommand` of the user's SSH configuration (such as `gcloud` from `/opt/homebrew/bin`), and an embedded server's managed jobs. Terminals are not affected; their login shells set their own. So on macOS and Linux `run` first calls `splitty_tauri_lib::login_path::adopt`, while the process has no other thread: unless standard input is a terminal, it runs `$SHELL -l -i -c` (csh/tcsh `-i -c`) with `/usr/bin/env` between two markers, reads the output up to the closing marker for at most 5 s (a background program of the startup files may hold the pipe open much longer), and sets `PATH` to the login shell's entries followed by the inherited ones it lacks. Only `PATH` is taken. A daemon has the `PATH` of whatever started it; the Electron shell does not do this yet.

The main window gets its native commands only on its own backend's origin. Instead of a capability file for every `http://127.0.0.1:*` page, the Tauri app adds a capability at runtime (`splitty_tauri_lib::capability`) for the window `main` and the exact origin `http://127.0.0.1:<port>`: at setup on macOS and Linux, and on Windows when `wsl_start_backend` learns the port, before the setup page navigates there (one per port; after a distribution switch the old one stays registered, behind the navigation guard). The bundled Windows setup page keeps its static capability (`capabilities/setup.json`).

**Remote windows.** A desktop app can also show a host's UI with no local server at all, on Windows without WSL (`desktop-remote`). The trusted UI, the main window on its backend or the Windows setup page, asks the shell to open a host. The native process runs the connect flow itself (Tauri: `tunnel::open` in `splitty_tauri_lib::remote`; Electron: `splitty connect <target> --no-open --json` per window), reports its steps to the calling window and holds the tunnel. Only when the host's UI is ready does it open a window `remote-<n>` straight onto the single-use session URL, so the bootstrap code never passes through the trusted UI, and no window that runs host code ever showed a local page. There is one window per target: opening it again focuses the window, or reconnects it in place after its supervisor gave up (10 minutes, as `connect`), and concurrent opens share one attempt. The window's task supervises the tunnel until the window is destroyed. The page reconnects by itself while the same daemon answers; a restarted daemon gets a new session URL loaded into the window, and the title says `(reconnecting…)` or `(disconnected)` meanwhile. Tauri drops the page's leave prompt (`beforeunload`) in remote windows, since WebKitGTK would show it and hold up that navigation, and leaving loses nothing: the sessions are the daemon's. Closing the window ends its `ssh`, never the host's daemon; on the app's exit the remaining tasks are dropped, which kills their `ssh`. A remote window shows code from the host, so it is unprivileged:

- its label is in no capability (Electron: no preload), so it can call no native command;
- its cookie store is its own and in memory only (Tauri: `incognito`, on Windows also a WebView2 data folder per window, since WebView2's InPrivate webviews share one session per folder; Electron: a non-persistent partition per window), so the host's session cookie reaches no other server;
- it navigates only within its tunnel origin; other web URLs go to the system browser, and everything else is blocked, the shell's bundled pages included;
- it opens no windows, the UI's own pop-outs included;
- it has native decorations, and the UI behaves as in a browser (a session URL with `host`).

The Tauri app records recent hosts in Splitty's configuration directory on macOS and Linux, shared with the CLI, and in the app's own on Windows.

`splitty daemon start` binds the listener in the foreground, then re-executes its own binary as a detached `splitty daemon run` process (new session, stderr appended to `daemon.log`) that inherits only the bound listener. It does not fork, because the CLI already runs a multi-threaded Tokio runtime. The command waits up to 10 s for the daemon's readiness line on a stdout pipe (`SPLITTY_DAEMON_READY` or `SPLITTY_DAEMON_ERROR`), printed after the control socket was bound or skipped and `daemon.json` was written, and only then prints `SPLITTY_PORT` and exits 0.

## Remote Hosts

`splitty connect` reaches a host only through the system `ssh` (`splitty-remote`); on Windows that is `%SystemRoot%\System32\OpenSSH\ssh.exe` when it exists and `ssh` from `PATH` otherwise, started without a console window. What `ssh` sends is one command line that the host's login shell parses again, so every remote command is a `CommandLine` of constant words and values passed through `quote`, sent as the one argument after `--`. The scripts it runs (probe, install) are constant single lines without single quotes, run as `sh -c '<script>' <name> <quoted values>`, so fish and csh login shells only parse that outer line.

Before connecting, the client probes the host once (kernel, architecture, `$HOME`, the marker of its own version) and, when its version is missing and it has a payload for the host's kernel (Linux or Darwin) and architecture, installs its server:

```
~/.local/share/splitty/remote/<version>/
  splitty              static server, run by its absolute path from then on
  shell-integration/   next to the binary, where the server looks for it
  .payload-sha256      checksum of the archive it came from
```

The archive goes over the connection's stdin into a `mktemp -d` directory (umask 077); `sha256sum -c` (or `shasum -a 256 -c` where that is missing, exit 5 without either) checks it before `tar` unpacks it, `splitty --version` must run, and only then is it moved to `<version>/`. Afterwards every other version directory whose binary no process runs is removed (the running executables from `/proc/*/exe`, or from `ps -axo comm=` on a host without `/proc`), so a daemon of an older version keeps running until the user restarts it. Payloads come, in this order, from `SPLITTY_REMOTE_PAYLOAD` (development), from archives built into the client (`crates/splitty-remote/build.rs` embeds the archives named by `SPLITTY_REMOTE_PAYLOAD_X86_64` and `SPLITTY_REMOTE_PAYLOAD_AARCH64` for Linux and `SPLITTY_REMOTE_PAYLOAD_DARWIN_X86_64` and `SPLITTY_REMOTE_PAYLOAD_DARWIN_AARCH64` for macOS at build time, keyed by kernel and architecture, with their checksums), or from the client itself when it is a static Linux build of a Linux host's architecture; without one, `splitty` from the host's `PATH` is used. The release builds the static aarch64 server and the two macOS servers first and builds them into the static x86_64 server (the WSL backend), which thereby installs on every supported host; `packaging/windows/build-wsl-payload.sh <repo> <out> [commit] [x86_64|aarch64|darwin-aarch64|darwin-x86_64]` builds each, aarch64 cross-linked with `rust-lld`, the macOS ones with `cargo zigbuild` and a zig pinned by checksum (`packaging/zig-toolchain.sh`, no Apple SDK; zig's linker ad-hoc signs the arm64 binary, as macOS requires). On a Mac the same script links the x86_64 Linux server with `rust-lld` too and the macOS ones with Xcode's linker; `packaging/macos/build.sh` builds all four into the local macOS app, as `packaging/windows/build.ps1` does for the Windows app.

On a macOS host, every command of the installed server runs as `env SPLITTY_CONFIG_DIR=<home>/.config/splitty <server> …` (`install::Server::Installed` carries the directory). `splitty_core::config::config_dir` (and the token's and the templates' directory) then is that directory, and the control socket's directory `run/` below it, so the daemon, its `daemon.json`, token, state and sockets never meet those of a desktop app or CLI of the same user in `~/Library/Application Support/splitty`, which the app attaches to without a version check. The daemon and its panes inherit the variable, so a pane's `splitty` reaches the same daemon. Linux hosts run without it. Listening ports are scanned from `/proc` only, so a macOS host reports none. The tunnel (`splitty_remote::tunnel`, shared by the CLI and the desktop apps) then talks to that server: `remote-handshake --json --ensure-daemon --port <P>` (format 1: the answering server's version, protocol and path, the daemon, started on `127.0.0.1:<P>` when none runs, and its screens) and, after the forward is verified, `issue-bootstrap`. `P` is a port the client holds free on its side, so a daemon it starts gets the same port on both ends; on reconnect it is the previous port, so a daemon restarted after a reboot keeps the origin. When the installed server is gone (a rebuilt container), the supervisor installs it again once.

`tunnel::open` runs the whole first connect (install, handshake, forward, first URL) and reports its steps through a callback (`install`, `daemon`, `started`, `tunnel`, and a notice when the daemon runs another version); a daemon older than the client that keeps its sessions, with the client's own server on the host, it updates on the way: `daemon stop`, then the handshake again, which starts the client's version, which adopts the sessions (`update_plan`; a newer daemon is never replaced, since an older version may not know keepers); `tunnel::supervise` then keeps the tunnel up and gives up after a time its caller sets (`connect`: 10 minutes). Both futures are `Send`, and the `ssh` of a tunnel is killed when it is dropped, so a desktop app runs them as tasks and ends a window's tunnel by dropping its task. `RemoteError::failure` gives every failure one message and, where there is one, a hint (host key, busy port), which `connect` prints as text or, with `--json`, as the `failed` event of one JSON object per line (`tunnel::ConnectEvent`: `progress`, `notice`, `ready`, `forward`, `lost`, `retry`, `restored`, `url`, `failed`, `closed`) for the Electron shell. `tunnel::open_forwarding` puts the ports of `connect --forward` into the same `ssh` (`-L 127.0.0.1:<local>:localhost:<remote>`, ahead of the daemon's forward, so the verified daemon port means they are bound too), each on its own port here when that is free on `127.0.0.1` and `::1` and on any free port otherwise, and the supervisor holds and rebuilds them on those ports like the daemon's; they are announced as `localhost`, whose cookies are not Splitty's.

The hosts a user knows (`splitty_remote::hosts`) are the recent hosts and the configured ones. A successful `connect` records its target in `recent-hosts.json` in the configuration directory (`{"version":1,"hosts":[{"target","lastConnected"}]}`, most recent first, at most 20, written to a fresh 0600 file and renamed over the old one; a file that does not parse counts as empty). The configured hosts are the concrete `Host` names of `~/.ssh/config` and the files its `Include`s name (`~`, paths relative to `~/.ssh`, `*` and `?`), read and never written; patterns, negations and `Match` are skipped. The hidden `splitty remote-hosts --json` prints both, recent first, for the Electron shell's host picker. Host display aliases and hidden markers live in private atomic `remote-host-preferences.json`, keyed by the unchanged SSH target; the order in which the user arranged the host groups lives in `remote-host-order.json` beside it, a file of its own because the preference reader rejects unknown fields and an older Splitty would otherwise read every alias as gone. Aliased targets remain discoverable beyond recent-history eviction. Metadata mutations share an OS file lock across hub and desktop processes. Explicit CLI/desktop connections reveal targets; automatic hub reconnects only record visible hosts.

`splitty remote-bridge` (module `host`) is the channel a relaying client (the hub, see Remote Screens) uses: it obtains a WebSocket ticket from the daemon on the host with the user's own token file, opens `/ws` with the daemon's origin, and carries the WebSocket's messages over its stdin and stdout as frames (kind byte, big-endian length, payload; `splitty_remote::bridge`). Nothing secret crosses SSH. Daemons record their protocol version (`PROTOCOL_VERSION`, 1) in `daemon.json`, and the handshake reports it, so such a client can decide whether it can talk to an older daemon.

## Remote Screens

The local server is a transport hub for screens of other hosts (`splitty_server::hub`). The window opens `/ws/remote?ticket=…&target=…`, which passes the checks of `/ws` (Origin, `Sec-Fetch-Site`, single-use ticket) and is not on the control socket. For each socket the hub runs the start of `splitty connect`: the install, then the handshake with `--ensure-daemon` and a port hint held free on this side, so a later `connect` can forward the same port. The protocol check accepts the daemon's protocol if it is the hub's `PROTOCOL_VERSION` or the one before; otherwise the hub answers `incompatible` and leaves the daemon running. Then it starts `remote-bridge` on the host, by the installed server's path, and waits for the daemon's `mux.welcome` through it. Meanwhile it reports `remote.progress`; then it sends one `remote.ready` (the daemon's version and protocol, whether it started it, the host's screens) and records the target as a recent host. From then on it relays the daemon's messages verbatim both ways and never reads, rewrites or merges them: ids stay apart because the client holds one connection per host, not because the hub translates them. When the bridge ends, the hub closes the socket with 4001; when the socket closes, it closes the bridge's input and kills its `ssh` after a short grace. A failure before the relay is one `remote.error` with a code, a message and, where there is one, a hint (`hub::failure` maps the SSH, install and handshake errors).

Every socket has `ssh` processes of its own, opened with `Ssh::stdio_only` (`-T -a -x -o ClearAllForwardings=yes` on top of the hardening options), so the user's configuration adds no terminal and no agent, X11 or port forwards; two windows on one host hold two bridges. Nothing but the commands of the install, the handshake, the update's `daemon stop`, the bridge, the client's messages and, for a shared port, `remote-relay prepare` and `remote-relay serve` reaches the host. `GET /api/remote/hosts` lists the known hosts of the user the server runs as. The `Connector` trait separates the flow from `ssh`, so the hub's messages, error codes and relay are tested in-process against a scripted host whose bridge is a local `sh`.

With `update=1` the hub updates the host: the handshake starts no daemon when one runs, so its answer tells the running daemon's version without a call of its own. When that daemon already ran and its version differs from the hub's, the hub runs the installed server's `daemon stop` (any version's stops the daemon `daemon.json` names; a daemon with keepers leaves its processes running for the new daemon to adopt, an older one ends them and the new daemon restores the workspace it saved, with new shells), reports the step `update`, and runs the handshake again, which starts the hub's version; it stops nothing when the host has no server of the hub's version to start. The hub also keeps the client's remembered remote screens (`hub::remembered`): `GET` and `PUT /api/remote/screens` read and replace `remote-screens.json` in the configuration directory (`{"version":1,"screens":[{"target","screenId","name"?,"position"?}]}`, at most 200, each target valid and each (target, screen id) once, written like `recent-hosts.json`), apart from the workspace persistence, so it works with an embedded server too.

Every daemon reports the TCP ports processes of its sessions listen on, which a client can forward. On Linux, `splitty_core::pty::ports` reads `/proc/net/tcp` and `tcp6` for the sockets in state LISTEN on loopback or wildcard addresses, the parent pid in every `/proc/<pid>/stat` for the process tree of each session's shell, and the `socket:[<inode>]` links in `/proc/<pid>/fd` of those processes; a port held in two sessions counts for the lower session id. `ws::ports` runs the scan on a blocking thread every 2 seconds while a client is connected and sends `ports.changed` with the full list right after each `mux.welcome` (also when it is empty) and to every client when the list changes; other systems send nothing. Through the hub it is just one of the host daemon's relayed messages.

The hub forwards discovered or manually entered ports (`hub::forwards`, `/api/remote/forwards`, excluded from the control socket). Each uses an owned foreground `ssh -N -T -a -x` (`Ssh::forward_only`, `tunnel::PortTunnel`) with the hardening options and `-L 127.0.0.1:<local>:localhost:<port>`. Unsaved forwards default to the remote port when free or a free alternate; saved and explicitly requested local ports are exact. Selection checks both IPv4 and IPv6 loopback, including each alternate candidate. Unsupported IPv6 permits IPv4; occupancy, permission and uncertain errors fail closed. The IPv6 probe closes immediately, and checks repeat immediately before SSH handoff and after verification, including rebuilds. A later independent IPv6 bind after establishment remains outside that guarantee.

`PortTunnel` verifies ownership before announcing `http://localhost:<local>`. OpenSSH runs local forwarding setup before `LocalCommand`; `ExitOnForwardFailure` prevents that command when binding fails. A fixed `LocalCommand=echo SPLITTY_FORWARD_READY_V1` produces a bounded stdout marker (4 KiB, LF/CRLF), followed by the TCP/liveness check. No target, label or other input is interpolated into executable text. `ControlMaster=no`, `ControlPath=none`, `ControlPersist=no` and `ForkAfterAuthentication=no` prevent reuse or backgrounding from bypassing this proof or losing process ownership. Configuration lookup and readiness each time out after 15 seconds. An authenticating process plus somebody else's listener cannot count as ready. The constant command is limited to hub `PortTunnel`; the CLI daemon-tunnel flow is unchanged. `ssh -G` still rejects configured extra forwards because `ClearAllForwardings` would also clear the requested `-L`. Service HTTP, HTTPS and WebSocket traffic remains raw TCP with no added Splitty credentials.

Saved preferences are separate from live state. `hub::preferences` validates `remote-forwards.json` in the private config directory, with atomic owner-only replacement through `hosts::write_private`: version 1, canonical target and remote-port keys, local port, label (at most 200 Unicode characters), and enabled state. It bounds saved entries at 32 per host and 256 total, including disabled rules. Missing, unreadable or invalid files read empty without repair. GET/PUT/DELETE `/api/remote/forward-preferences` are guarded metadata operations that neither reserve ports nor contact hosts. PUT merges only supplied fields and preserves existing enabled state; creating from a live forward captures its actual local port. Runtime `lastError` is joined into GET but never persisted. Active GET keeps its original array of `up`/`down` records.

Only a successful send of `remote.ready` schedules restoration of that host's enabled inactive mappings. Tasks reread current consent, reuse existing openings and never delay the relay or add hub frames. Startup, login, reads and metadata edits remain passive; discovery is unnecessary. An initial failure records `lastError` and waits for explicit action or another successful readiness event. A live supervisor survives screen detachment and Forget, keeps its selected port through loss and rebuild, reports `down` and retries with growing waits up to 10 seconds. Active/opening capacity is separately bounded at 32 per host.

A per-key asynchronous mutation lane covers start, Stop, Forget, metadata merges and cleanup. Short shared locks locate lanes, claim capacity and atomically merge storage; none spans another key's SSH wait. Hub-owned operation tasks retain their owned lane even when an HTTP caller disappears. Stop saves disabled state before closing, and waits for the supervisor, including a bounded in-flight rebuild and child reap, before releasing the lane. A failed durable Stop leaves the live forward alone. Explicit successful POST enables an existing preference and persists an alternate only after verification; a failed commit closes the new tunnel before later mutations proceed. Forget removes only the rule and runtime error, leaving any live tunnel supervised. Automatic POST rechecks disabled consent and refuses with `forward_paused`; no earlier queued restore or cancelled request can undo an acknowledged Stop or Forget. `Connector::forward` and deterministic setup/stop barriers exercise these paths in-process; dropping the hub cancels its operation tasks and supervisors.

Reverse forwards share a port of this machine with a host (`hub::reverse`, `/api/remote/reverse-forwards`, `/api/remote/reverse-forward-preferences`, excluded from the control socket). They reuse the forwards' shape: per-key lanes, an `Opening` slot, a supervisor that rebuilds with the same ports and reports `down`, 32 active per host counted apart, and opt-in rules restored after `remote.ready`, but in `remote-reverse-forwards.json`, since `remote-forwards.json` refuses unknown fields. `Connector::reverse` runs the install's prepare (Darwin is refused: the owner check needs `/proc`), `remote-relay prepare` over a stdio-only `ssh` for the host's private relay directory (`<run dir>/relay`, 0700), then `tunnel::ReverseTunnel`: one owned `ssh -T -a -x` (`Ssh::relay_only`; no `ClearAllForwardings`, so configured forwards are refused as for `PortTunnel`) with `-R <dir>/<16 hex>.sock:localhost:<local>` and the command `remote-relay serve`. `sshd` binds the remote end as a Unix socket, to which `GatewayPorts` does not apply. `host::relay` checks the socket (inside the directory, a socket of its user, made 0600), binds `127.0.0.1` and `::1` on the port, prints `SPLITTY_RELAY_READY_V1` (or `SPLITTY_RELAY_FAILED_V1 <code>`) and relays a connection only when `pty::ports::connection_owner` finds the client socket's uid in `/proc/net/tcp(6)` equal to its own. `ReverseTunnel` reads that report (4 KiB, 20 s) and then writes a heartbeat line every 10 seconds; the relay ends at end of input or after 45 seconds without one and removes its socket, so a lost connection frees the host's port before a rebuild can take it again. The local server's own port, which `remote_upgrade` and the routes hand the hub from `listen_addr`, is never shared.

On the client, a host is a connection like the local server (see Client connections), opened lazily: "New screen on host…" (the arrow next to New screen in the drawer, a host caption's +, the command palette) picks a target from `/api/remote/hosts` in the host picker the remote windows use, and `ensureRemote` (`lib/connection/registry.ts`) opens the host's connection if the window has none yet. The connection goes when its last screen leaves the window and the user is not explicitly browsing that host, which ends the socket's `ssh`. Its socket, `RemoteSocket` (`lib/remote/remote_socket.ts`), has the hub's two phases: before `remote.ready` it accepts only the hub's messages and collects the progress, anything else ends the attempt; after it every message reaches the connection's handlers except `remote.*`, which only the host could send then. Messages sent while it does not relay wait for the next `remote.ready`, typed input excepted. A drop after `remote.ready` (4001, or the local server gone) marks the host reconnecting and retries with a fresh ticket per attempt and a delay growing to 10 seconds, until a code retrying cannot fix (`failed`) or two minutes without success (`offline`); a failed first connect, and a failed ticket request, end in an error with a retry and never in the local login dialog. `stores/connections.svelte.ts` mirrors each host's phase, progress, error, daemon version and the screens it could reopen for the UI.

A remote screen is a reference: a random window key, its connection, and the screen's id on the host. `RemoteScreenSync` (`lib/mux/remote_screen_sync.ts`) is the host's screen sync. It never creates a window screen from a welcome or a snapshot; every welcome, the first and the one after each reconnect, resyncs the open screens the host lists, whose snapshots rebuild the panes and re-attach their sessions, and flags an open screen the host no longer lists as missing. A new screen gets its `create_screen` exactly once, after the welcome and once its view is ready, with no local shell profile. Before that, when the host runs screens the window does not show, the new screen offers to open them instead (the reopen offer, with each screen's name and pane count); opening one binds a window screen to its id and builds it from its snapshot. The screen shows its state inside itself (`components/workspace/RemoteScreenStatus.svelte`, derived by `lib/remote/screen_status.ts`): the connection's progress with Cancel, an error with its hint, details, Copy and Retry, the offer, reconnecting, offline, missing on the host; meanwhile its panes are inert. The screen list shows each host's caption with a state dot above its screens.

Closing a remote screen (`lib/remote/close_screen.ts`) detaches it without asking and says so in a notice with Reopen; ending it is a second button in the drawer's row, with an inline question the first time. Detaching removes the screen's binding first, so no layout op is sent for it, and its panes only detach (the binding's `detach` teardown): its sessions keep running on the host, and the reopen offer and the host group list it again. Terminating sends the host one `close_screen`. Closing the window's last screen creates a local one first. Quitting or reloading only detaches, since the host keeps its sessions when the socket closes, and the quit guard counts local sessions only.

The local server remembers the window's remote screens (`lib/remote/remembered.ts`). After every change of the remote screens or their places (create, open, detach, terminate, remove, a name from the host's snapshot, a move), the client writes the list with `PUT /api/remote/screens`, 400 ms after the last change, one request at a time, and at once with `keepalive` when the page goes (`pagehide`): each remote screen's target, id on the host, name and index in the window's screen list, local screens included. A new screen whose `create_screen` is not sent yet is left out, a screen missing on its host stays until it is removed. On start the client reads the list and waits for the local server's first welcome, so `ScreenStartup` and its placeholder see local screens only; then it inserts the remembered screens by position, each at its index or at the end when the list is shorter, which with the same local screens gives the old order. Nothing is written before the list was read and restored, and nothing after a failed read, so a page cannot wipe the list. A restored screen has no binding, and so no layout, until its host's connection exists: the connection opens when the screen becomes the active one (`hostToConnect`), or when the host is connected for another of its screens, and an unreachable host costs nothing at start. Until then the screen list shows the screen with a hollow dot. A screen bound after the host's welcome that the welcome did not list is flagged missing like any other, with Remove.

The drawer's screen list (`components/chrome/Drawer.svelte`) shows local screens and then, per host with open screens, one caption line above that host's screens (`lib/remote/on_hosts.ts`, `screen_groups.ts`); the rows themselves are the same as local ones. The caption carries the host's identity and state dot, a button for its ports when it has any, and a + for a new screen there; a click on it opens the Hosts panel at that host. Hosts without open screens are only in the Hosts panel (`HostsPanel.svelte`), the drawer's third panel next to Settings and Templates. The display, numbered shortcuts, the wheel over the drawer and the title-bar wheel share the same flattened group order: local first, then hosts in first-open-screen order. The wheel over the drawer switches screens instead of scrolling it, and the list keeps the active screen in view. Dragging reorders only that group's slots in the underlying list, preserving the remembered-screen format and other groups' positions.

The host directory combines open and connected hosts with recent hosts and the last observed catalog (`lib/remote/host_directory.ts`). Never-used SSH-config aliases stay in the picker. The hub's private `hub::catalog` persists `remote-catalog.json`: authenticated `GET /api/remote/catalog` reads the versioned directory, and `PUT` replaces only the named host with a server timestamp. A mutex serializes atomic owner-only writes; at most 20 hosts with 200 screens each survive. This is separate from the remembered open-screen list: reading the catalog never opens a screen or an SSH connection. Each first welcome replaces the observed list, including an empty one; snapshots and this window's renames, pane changes, detach and terminate update it. The client coalesces writes for 400 ms and serializes each host's writes, protecting newer observations from late reads and replies. `HostPreferences` reads and changes aliases through `/api/remote/host-preferences`; `HostOrderStore` (`lib/remote/host_order.ts`) loads the arranged host order through `/api/remote/host-order` (also when the window gains focus, for another window's change) and replaces it after the user drags a host group by its caption in the drawer, into the screens store, which `orderedScreens` and `hostGroups` follow, so drawer, navigation and shortcut numbers keep one order: local screens, the arranged hosts, then the others in first-appearance order; `DELETE /api/remote/hosts` persists hiding and clears recent/alias/catalog data. The client serializes same-target metadata mutations and suppresses late catalog replies and observations for hidden targets. Existing screens and forwards keep their lifetimes. Explicit re-addition writes `hidden:false` before connecting, including when an existing connection is already ready. Fresh screen defaults count independently per connection from Screen 1, reserving known unopened names of that host.

The Hosts panel keeps disconnected hosts with last-seen names and pane counts. A host with open screens starts unfolded, any other folded; unfolding a disconnected host connects and refreshes the directory without a placeholder screen, and folding it, or closing the panel, releases that browsing interest and closes the connection if no screen remains open. Expanded state never causes connections on reload. The connected directory is the latest welcome plus changes observed in this window, not a continuously polled cross-client list. Opening a cached or available screen attaches to its existing id; a missing one is reported rather than recreated. New screen in a host's caption or panel entry deliberately creates one; the general picker, and a host picked under the arrow next to New screen, retain the reopen offer. In the desktop app the panel and that menu also open a host in a remote window, through the host picker of `App.svelte` started with that target.

The host caption's tooltip says when a daemon runs another version than the local server (`/api/build`). An incompatible host's screens offer "Update now…", and the Hosts panel offers "Update…" for a connected host of another version; their dialog names both versions and what the update does on the host (`lib/remote/update.ts`). For a daemon that keeps its sessions (`keepsSessions` in the incompatibility error or the last `remote.ready`, from the handshake, from `daemon.json`), it says that they keep running while the daemon restarts; for any other, what ends: the handshake screens carried in the incompatibility error, or the last `remote.ready`, with this window's own pane counts where available. A host that cannot report counts is labelled unknown. Once confirmed, `RemoteSocket.retry({ update: true })` opens only that attempt with `update=1`, and the screen shows its progress, the update step included; a connected socket first lets its connection go as a drop would, so the host's screens wait and resync as after one.

The client's half of the ports is one `PortForwarding` per window (`lib/remote/port_forwarding.ts`, pure validation/joining in `lib/remote/ports.ts`, view state in `stores/ports.svelte.ts`). It watches remote connections' `ports.changed`, keeping bounded plain-text process names and at most 256 checked ports; disconnection clears discovery only. The drawer joins discovery, saved preferences and live forwards into one row per target/remote port, including disconnected hosts and services discovery never saw. Paused consent, initial restore errors and an established tunnel rebuilding are distinct states.

Inspecting ports never acquires a browsing connection: the caption's ports menu lists a host's forwarded ports with Open and its detected ones with Forward and open, and links to the Hosts panel, where each host lists its forwarded and saved ports before the ones only detected. A row shows one action (Open, Forward, Resume or Retry, `portPrimary`) and keeps the rest in a menu (`portMenu`, `components/chrome/remote_view.ts`). Per-host forms fix their target; the panel's global form supports arbitrary targets. The view components only delegate explicit actions to the existing controller; presentation helpers do not infer tunnel health from the host screen connection or start forwarding.

Both APIs refresh on window start, after mutations, after host readiness, on focus and when the Ports view opens. They poll every five seconds while there is a watched host, active forward, saved rule or open view. Failed reads preserve the last valid state; read generations and per-key mutation ordering prevent stale responses from repainting stopped/forgotten entries or opening old links. Refresh never POSTs or restores enabled rules itself. This also lets another window observe saves, pauses and removals when no live forward exists.

Manual entry accepts target, remote port and optional exact local port. Save without starting sends only preference PUT, even while disconnected. Forward mutates active state with POST; Remember is opt-in and saves the returned actual port afterward, reporting a save failure while leaving the successfully opened tunnel visible. After these mutations, a fresh `cache: no-store` active GET must confirm the same up mapping before publication or navigation. A delayed POST response therefore cannot authorize an old link after that GET observes another window's Stop, remap or dropped tunnel. Only the current key is reconciled, with its generation checked after the final asynchronous read; failed validation closes the pending browser tab without retrying POST. The read is a snapshot, so later independent changes remain possible. Labels use bounded plain text with control/bidi filtering. Stop durably pauses a saved rule; Resume/Retry and an explicitly chosen alternate send explicit POST. Forget removes the saved rule and explains that a live tunnel keeps running until Stop or server exit. A different local port for an active mapping is refused until it is stopped.

A port that appears brings no notice; the host's port lists offer it. `remote.autoForwardPorts` stays off by default; with it, a port that appears after a host's first discovery list after connection or reconnection is forwarded once per connection and process, without a notice. Its automatic requests use `automatic:true`, respect paused saved rules and never silently remap saved-port conflicts. Opening a forward or clicking a link does not implicitly remember it; a link click is explicit consent to resume a paused rule.

A host's terminal pane passes an `openLink` to its emulator (`terminal_mount.ts`), a local pane none, so its links go to the system browser (`openExternalTarget`, web URLs only). OSC 8 hyperlinks of every pane are asked about first in a Splitty notice with Open (`lib/terminal/hyperlinks.ts`), since the link's text may hide its target; not with xterm.js's `confirm` and `window.open`, which the macOS desktop webview answers with false and Tauri would open inside Splitty. A desktop opener that refuses a link says so in an error notice. With `openLink`, xterm.js's detected links, its OSC 8 hyperlinks and ghostty-web's links (its own providers registered again with the click handed over; the later registration replaces the built-in links in its cache) go to `PortForwarding.openLink`. A link whose host is `localhost`, `127.0.0.1`, `0.0.0.0` or `[::1]` opens at the forward of its port, the scheme's when it names none, rewritten to host `localhost` and the local port with scheme, path, query and fragment kept; without a forward the click opens one first, since the click is the consent. Saved-port conflicts report an error without opening an unrelated local service; a newer Stop cancels an old link continuation. Every other link opens as it is. In a browser an address opens in a blank window cut from Splitty's (`opener` null); a window the browser blocks, as it may after the wait for a forward, is offered in a toast whose click opens it.

**Editor handoff.** Terminal and tab context menus offer one "Open Folder in" submenu for VS Code and Zed, and for a remote terminal also an SFTP client (`sftp://<target>/<path>/`, handed to the OS's handler for `sftp:` links, for moving files to and from the host). The selected pane’s `ScreenBinding` supplies its local/remote connection and its session’s cwd. `lib/remote_editor.ts` rechecks both at click time; `lib/editor_target.ts` validates data and generates fixed editor folder URIs. Browser dispatch is synchronous within that deliberate click. Tauri’s `editor` component and Electron’s dedicated editor handlers independently validate the editor enum, absolute directory, optional SSH target and local WSL distribution before generating the URI and handing it to the OS. Remote IPC retains `open_remote_editor` / `editor:open-remote` with optional `editor` (default VS Code); local IPC uses `open_local_editor` / `editor:open-local`. Tauri grants both commands only to the main window on the exact backend origin; Electron also requires its top frame. Generic openers remain HTTP(S)-only and isolated remote windows gain no permission. No server command, terminal output or query enables the action. The UI reports requests and observable failures, with editor-specific setup guidance, without claiming installation detection or successful connection. For the editors, explicit ports/IPv6 require local SSH aliases and VS Code also rejects all-hex authorities; the SFTP link carries every target form unchanged, an alias included, which only clients that read the SSH configuration resolve. Local folders use the editor’s file URL; VS Code WSL folders use `wsl+<distro>` from `/api/build`. Zed for local WSL folders is disabled because its URL parser has no WSL connection form. Remote menus also copy SSH paths (`target:/path`, or `ssh://target/path` for a port).

**CLI editor requests.** `splitty open` resolves an existing file or directory on the originating server and posts its session ID, absolute path and optional editor to `/api/editor/open`. The owner control socket and authenticated HTTP listener expose this endpoint; restricted grant sockets do not. `ws::editor` selects exactly one registered (`editor-open-v1`, `editor.register`) connection streaming that session, caps admission to one pending request per client / 32 global / one per two seconds, and waits up to 30 seconds for that same connection's `editor.result`. No recipients or several recipients fail explicitly. Disconnect and detach cancel; pending requests are never stored in workspace state or replayed. Subscription membership comes from the core protocol connection, not pane IDs supplied by the request.

`lib/editor_requests.ts` runs only in the trusted hub, derives the host from its `ServerConnection`, validates the path/editor/kind, and offers a bounded prompt. Only a deliberate click can dispatch a fixed editor URI. Local requests require loaded build metadata to distinguish WSL from native paths. The action rechecks session identity, WSL context and deadline and consumes the request synchronously. Cancellation, session closure, disposal and reconnect invalidate saved actions. The native APIs accept optional `kind` (`folder` by default); files omit the trailing slash and reject ambiguous colon syntax. The CLI reports dispatch, never successful editor connection. Local `editors` preferences choose file/folder defaults, extensions and project rules (`local` or `host:<exact SSH target>`, longest directory prefix). They cannot waive confirmation or be supplied by a remote request. Remote-owned windows keep their existing isolation and do not register.

## Module Map

The module-level map of the Rust crates is the architecture model in [`architecture/`](../architecture/README.md): every crate and top-level module as a component, with its description, its capability under `openspec/specs/`, and the dependencies allowed between components. `cargo test` checks it against the code in both directions (`architecture/check`), so it stays current; read the `.c4` files or query `likec4 export json` as the README shows. `mux::effect_runner` is a component of its own there, so "within the mux, only the effect runner touches the PTY layer" is a checked rule.

The desktop app (`splitty-gui`) links `splitty-core` and `splitty-server` on macOS and Linux only, since Windows runs the server in WSL, and `splitty-remote` on every platform, for remote windows.

The model stops at the web frontend as a container. Its entry points:

```
frontend/src/
  lib/protocol/types.ts     TypeScript types (mirrors Rust types)
  lib/connection/           Server connections, screen bindings, routing, screen sync
  lib/remote/               A host's hub socket, its API, remote screen status, detach and terminate,
                            the remembered list, host directory and grouping, the update warning
  lib/mux/remote_screen_sync.ts  A host's screen sync (references, reopen offer, create once)
  lib/mux/mux_client.ts     A connection's mux client (ops, welcome, spawn waiters)
  lib/terminal/session_client.ts  A connection's sessions (create queue, pane tables)
  layout/screen_snapshot.ts  Rebuild dockview layout from ScreenState snapshot
  stores/screens.svelte.ts   Client-side screen management (each screen with its connection)
  stores/connections.svelte.ts  Host connections as the UI shows them
```

OSC 52 clipboard writes in the xterm renderer use `clipboard_policy.ts`: enabled by default, capped at 64 KiB of UTF-8, with a brief success notice (no clipboard contents). Failed writes show an error. Reads always return empty. `terminal.allowOsc52Write` is persisted by the server and can disable writes. Replay filtering prevents historical copies from replacing the current clipboard.
